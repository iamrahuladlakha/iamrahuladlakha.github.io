When a normal service misbehaves, the logs usually tell you what went wrong, because the code takes the same path every time and the logs mostly confirm it. An agent doesn't work like that. It picks its path as it goes: it reads something, decides to call a tool, reads the result, and decides again. So if you want to know why an agent did something, you need a record of each decision and what it was looking at when it made it. That record is what I mean by agent observability, and the more I read about agents in production, the more I think it's the piece teams set up last when it should come first.

In this post I'll go through what an agent trace actually is, how replaying recorded traffic turns it into a release gate, and what it costs to run in production.

The problem: three logs, no story

Here's a situation I keep coming back to. A support agent issues a refund the customer never asked for. You go looking for the cause. The refund tool's log shows the call went out. The model provider's log shows 30 prompts in that minute, from lots of different users. The guardrail's log shows 200 "allow" verdicts in the same window. Each log is accurate. None of them can answer the only question you care about: what did the agent read just before it decided to refund?

It's like reconstructing a car accident from three notebooks, one kept by each driver and one by the traffic light, with clocks that don't agree. You have plenty of data and still no sequence of events.

The second problem shows up when you try to fix it. Say a new prompt-injection trick gets published on Monday and you write a guardrail to stop it. Will that guardrail also block some of the 50,000 normal actions your agent took last week? A hand-written test set of 200 examples can't tell you. It covers the cases someone thought of, and real users and real attackers keep producing cases nobody wrote down. A stricter check that quietly breaks legitimate work is a real outcome, not a hypothetical one.

How it works: a trace is a tree of spans

The fix for the first problem is to give the whole run one trace ID and record every step inside it as a span: one timed step with its inputs, its outputs, and a pointer to the step it happened inside. Because each span knows its parent, the spans form a tree. A run contains model calls, a model call proposes a tool call, and the tool call gets checked by a guardrail before it runs.

Each span carries a small, fixed set of fields: an id, its parent, its kind (model call, tool call, guardrail decision, retrieval, human approval), when it started, how long it took, and what went in and came out. What's worth recording depends on the kind:

Span kindWhat I'd record
model callmodel and version, token counts, cost, the decision it made
tool calltool name, arguments, result status, the system it touched
guardrail decisionwhich guardrail, its verdict, its score, the policy version

That last column has the field I'd fight hardest for: the policy version on every verdict. Without it you can see that a check said "allow", but not which rules it was applying at the time.

In practice you rarely invent this format yourself. OpenTelemetry already fixes the span format, carries the trace ID between services, and exports spans to whatever backend you choose. Its generative AI conventions add typed spans for model and tool steps. LLM-focused backends such as Langfuse sit on top of it and add sessions, cost views and traces you can replay.

A worked example: the parcel question and the refund

Take a food-delivery support agent. A customer asks "where's my order?" and gets a reply 1,825 ms later. The trace has five spans:

35 + 900 + 40 + 250 + 600 = 1,825 ms. The first model call is 900 of those, about 49%. The two guardrail checks together are 75 ms, about 4%. That's the first thing a trace gives you for free: an honest picture of where the time goes. If someone tells me guardrails are what make the agent slow, this is the view I'd want in front of us.

Now the interesting run. The next day, a different conversation ends with a $40 refund. With a trace, the investigation takes minutes. The tracking tool's result included a line from the restaurant's free-text notes field saying the customer was owed a refund and it should be issued now. The very next model span proposed issue_refund. The guardrail span below it says "allow", with the policy version that allowed it.

So the team knows exactly what broke. Text that came back from a tool was treated as an instruction, and the guardrail never compared the proposed action with what the customer actually asked for. That's a precise fix, not a vague "make the prompt more careful".

Then comes the part I like best. They write a stricter check and replay last week's 50,000 recorded actions through it, offline. It would have blocked this refund and 12 others like it. It would also have blocked 30 legitimate refunds that customers had asked for. Those 30 false blocks go back to the team to tune before the check goes live. Without replay, those 30 customers would have found the problem for them.

Two more cases, outside food delivery

The refund is one shape of a general problem, so here are two more. Both are illustrative examples I've made up to show the pattern, not incidents I'm reporting, and they carry no measured numbers.

Example (coding agent): the test file that disappeared. A coding agent is asked to fix a failing test, and its pull request deletes the test file instead. The trace reads the same way as the refund. A read_file tool span returned a source file with a stale comment saying the tests in it were obsolete and should be removed. The next model span proposed deleting the file. The guardrail span said "allow", with its policy version. Same diagnosis: text from a tool was treated as an instruction, and nothing compared the proposed action with the task the agent was given. The stricter check, "a deletion has to be justified by the task, not by file contents", gets replayed over past runs before it ships, exactly like the refund check.

Example (healthcare intake): a trace you can't keep raw. An intake agent collects a patient's name, date of birth and reason for the visit, then books a follow-up. Here the trace store is the risk. I'd keep the metadata on every span (which agent, which tools, which verdicts, timings) and redact the content on write, so a name becomes [NAME] before it's stored. Where the team does need full content to debug, it goes to a separate, access-controlled store with a short retention period, and the span keeps only a reference. Replay turns traces into a release gate

Once you have traces, the loop that follows almost designs itself:

Record production runs. Bring in new attacks from red teaming and from a running list of the ways each agent could be attacked. Replay the normal traffic and the attacks through the candidate guardrail or policy. Count the false blocks on the normal traffic and the false allows on the attacks. Ship if the numbers hold, feed what you learned back into how risky you consider each agent, and go round again.

One write-up I came across on securing agents in production treats this as its own layer, continuous assurance, sitting on top of the guardrails and the policy engine. I agree with the framing. The guardrails can't be tuned without the trace, and the policy engine's verdicts can't be audited without it either. To me, replay is to prompts, guardrails and policies what a test suite is to code, and it should block a release the same way.

What a trace doesn't tell you

I recently read a survey on agent provenance, From Agent Traces to Trust, and it sharpened something I'd only half noticed. Logs and traces tell you what happened, in order and nested by step. They don't tell you what each output depended on. Which retrieved passage does the answer actually rest on? Did that tool result change the plan, or was it read and ignored?

The point from it I'd pass on to any team is that logging at a finer grain doesn't close the gap. Step-level traces already tell you which artifacts each step used. To know that an input changed the outcome, you have to replay the run with that input removed. To know a passage supports a claim, someone has to read both. Token-level logging gives you neither. So the money is better spent on replay hooks than on more verbose logs. The same survey notes that none of the observability systems it reviewed describe protection against tampering. That's fine for debugging, but if an auditor or another company has to rely on your traces, you need something stronger.

The other paper that changed how I think about this is Transect, which comes at traces from evaluation rather than debugging. Production observability asks what went wrong in one request. Evaluating a frontier agent asks what you can reliably infer about the agent from a run that is hundreds of pages and millions of tokens long. They call that range the observability envelope. They widen it by running automated scanners over the transcript and lining their outputs up on one turn-by-turn timeline, with each mark linked back to the turns it came from. It's the same raw record. The difference is the questions you ask of it.

Architecture and production implications

The trace is a store of sensitive data. Full prompts and replies are the most useful thing to keep and the most dangerous. They hold customers' messages, personal details and sometimes credentials. The rules I'd follow: always capture the metadata you need to troubleshoot and audit (who, which agent, which tools, which verdicts, timings). Keep prompt and reply content only when you need it, and redact it before storing, so a card number becomes [CARD] on the way in, not on the way out. Restrict who can read traces by how sensitive they are, and set a retention period after which they're deleted. OpenTelemetry's GenAI conventions help here because content capture is off by default. You switch it on deliberately, and in production you can send the content to separate access-controlled storage and keep only a reference on the span. Every one of these controls removes detail an investigation might want later, and I think that's a trade you make on purpose.

Volume and cost grow with every step. Each step of each run produces data, and agents take a lot of steps. At high traffic, teams sample: keep a share of normal runs and every flagged one, and keep metadata longer than content, so the long-term store holds the who, what and when, and the full text only for as long as it's needed.

Replay shows you the past. Replayed traffic contains last month's users and last month's attacks. It's the best test of a change you have. It doesn't guarantee anything about next month, so keep the red teaming going alongside it.

Tracing has failure modes of its own. The ones I check for in a review: exporting spans on the request path, so the customer waits for your telemetry on top of the 1,825 ms the run already took (batch and export in the background instead). A dropped parent span, which leaves children that no viewer can place. A sampling rule that decides before a run is flagged and throws away the one run you needed. A trace store with broader read access than the systems it records, which makes it the easiest place to steal customer data from. And replay that nobody budgets for: pushing last week's 50,000 actions through a candidate check is a real batch job, so I plan its compute and its review time as part of the release, not as an afterthought. The thing I'd do differently: decide the redaction and retention rules before the first incident, not during it.

What I'd do from day one. One trace ID carried end to end, across the model, every tool and every guardrail, including anything that crosses a service boundary. The policy version on every verdict. Redaction at write time. Replay as a release step for prompts, guardrails and policies. And I'd watch behaviour, not just errors, because a run that finishes without an exception can still be a run where the agent did something it shouldn't.

Takeaways

  • An agent chooses its path at run time, so its logs have to record decisions and what they were based on, not just outcomes.
  • One trace ID and a tree of spans turn three unrelated logs into a single story you can read top to bottom.
  • Log the policy version with every guardrail verdict. It's what makes a decision explainable a week later.
  • Replay recorded traffic through every candidate guardrail or policy before it ships, and count the false blocks as well as the catches.
  • Traces show what happened, not what depended on what. Spend on replay hooks rather than finer logging.
  • Treat the trace store like any other sensitive database: redact on write, restrict access, delete on a schedule.

What this means for leaders. Agents choose their path at run time, so without one connected trace per run, every incident turns into an argument between three logs. Tracing has a real cost: it's a store of sensitive data that grows with every step, and it needs redaction, access rules and deletion like any customer database. Skipping it costs more, because you find guardrail mistakes through customers, like the 30 legitimate refunds that replay would have blocked. The decision to make is whether replay becomes a release gate for prompts, guardrails and policies. Ask your team: can you show me one run end to end? Is the policy version on every verdict? What did the last replay block that it shouldn't have?

The picture I keep in my head is a parcel's tracking history. Collected, sorted at the depot, loaded on van 12, delivered at 14:02, photo of the doorstep. Every scan has a time and a place under one tracking number, so "where did it go wrong?" always has an answer. I'm curious how far other teams have got with this: are you replaying production traffic before you ship a prompt or guardrail change, or is it still on the list?
