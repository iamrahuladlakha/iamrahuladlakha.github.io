Here's a setup most teams building agents end up with. An agent decides to call a tool, the tool lives on a separate server reached over the Model Context Protocol (MCP), and that server runs a slow database query. The user waits. You open your tracing tool to find out why, and by default you get two traces. One ends at "called tool". The other starts from nothing on the server side. Nothing connects them, so you can't tell which agent decision caused which query.

That gap is what OpenTelemetry (OTel) is for. I'd treated it as background plumbing for a long time, the thing underneath the tracing dashboard. Once I went through how it actually works, and especially through the newer conventions for generative AI, I realised a lot of the design decisions in an agent platform come down to it. This post covers how it works, what the AI conventions add, and what I'd think about before putting it in production.

The problem: tracing falls apart in three places

A trace is one run of your system, recorded as a tree of timed steps called spans. Getting a clean tree is harder than it sounds, and it usually goes wrong in one of three places.

The recording code is tied to one vendor. Before there was a shared standard, every monitoring product shipped its own library, with its own calls and its own data format. Say you want LLM traces in one tool and server health in another. You end up instrumenting every request twice, in two formats, with two sets of bugs. Changing vendors means rewriting the instrumentation everywhere. It's like every courier printing a different shape of label, so switching couriers means re-labelling the whole warehouse.

The trace breaks at every program boundary. Inside one process, the "current span" sits in memory, so a new step knows who its parent is. Across a network call that memory is gone. Unless the caller sends its trace ID and span ID along with the request, the receiver starts a new, unconnected trace. That's the MCP problem above.

Recording mustn't slow the app down. If every finished span went over the network straight away, a service producing 30 spans a second would be making 30 upload requests a second. A slow tracing backend would then mean a slow app. And most of those spans are routine, so storing every one of them is expensive too.

How it works: two IDs, one header and a queue

OTel fixes all three with a small number of moving parts.

Every span carries two IDs. The trace ID is 16 bytes, written as 32 hexadecimal characters. The span ID is 8 bytes, or 16 hex characters. Sixteen random bytes give \(2^{128} \approx 3.4 \times 10^{38}\) possible trace IDs, so in practice two of them never collide and no service has to coordinate with any other to pick one. A span also has a name, start and end times, a parent, a status, and attributes (key-value facts such as the model used). Resource attributes describe the program itself, like service.name, and get stamped on every span that program produces.

One header carries the context across boundaries. The caller adds a W3C traceparent header to every outgoing request. It has four parts: a version (00), the 32-character trace ID, the caller's current span ID, and a flags byte, where 01 means "this trace is being kept". The receiver copies the trace ID, makes its first span a child of the caller's span, and respects the keep flag, so the trace stays whole from end to end.

MCP needed a variation on this. One MCP connection can carry many requests inside a single HTTP request, or run over a local pipe with no HTTP at all, so a header isn't enough. The MCP conventions put traceparent, tracestate and baggage into each request's params._meta field instead. The server span becomes a child of the client span. The HTTP request that happened to carry the message is recorded as a link (a pointer to a span that isn't the parent), because one MCP request might be retried over several HTTP requests.

Inside the process, a short pipeline moves spans out. Your code, or a library, calls a tracer to start and end spans. OTel keeps track of the current span even across async code, so nesting happens without you passing parents around. Finished spans go to a span processor. The batch processor queues them, and it's also the last place you can filter or mask data before anything leaves the program. An exporter then sends batches in OTel's wire format, OTLP, over HTTP or gRPC. (Not every backend takes both. Langfuse, for example, accepts OTLP over HTTP only.) A batch goes out when it hits a size limit or a time limit, whichever comes first, so those 30 uploads a second become about one. Optionally, a separate collector process receives spans from many services, applies central filtering, masking and sampling, and fans them out to more than one backend.

That's the "record once, export many" story. You instrument in one format and attach one exporter per destination. It's also why modern LLM tracing tools build their SDKs on top of OTel and not beside it: spans from LangChain, the Vercel AI SDK or vLLM land in the same trace automatically, and any language with an OTel SDK can send to them.

The GenAI conventions: agreeing on what a span means

A shared format still isn't enough if one library writes model and another writes llm.model_name. OTel's semantic conventions fix the names, and the GenAI set (everything under gen_ai.*) covers models, agents and tools. Every kind of step gets a fixed operation name and a span kind. CLIENT means a call out to another program, including the wait for the reply. INTERNAL means work done in-process. One agent run comes out like this:

invoke_agent support_agent          INTERNAL   the whole run
├── chat gpt-4o                     CLIENT     model asks for a tool
├── execute_tool lookup_order       INTERNAL   the tool runs
└── chat gpt-4o                     CLIENT     model writes the answer

There are also operations for workflows you define yourself (invoke_workflow), framework entry points (invoke_runner), a distinct planning phase (plan), retrieval, and memory reads and writes. An agent hosted by a remote service is still invoke_agent, but with kind CLIENT. A handoff to another agent through a tool is recorded on the tool span. If control comes back to the caller, the target agent's span sits under the tool span. If control is passed on for good, it becomes a sibling of the caller.

Three rules in these conventions matter more than they first look:

  • Names stay low-cardinality. A span name is the operation plus a stable target, like execute_tool lookup_order, and never a request ID. The agent name should be something meaningful. A framework class name like StateGraph doesn't count, and if there's no real name the attribute is left out altogether.
  • Sampling attributes go on at creation time. The operation, agent name, provider, model and tool name should be set when the span starts. A head sampler decides at that moment, so a rule like "keep every trace for the refund agent" only works if the name is already there.
  • One span per logical operation. A model call that the SDK retried automatically is one span covering all the attempts.

One caveat I'd flag in any design review: gen_ai.provider.name is the instrumentation's best guess. If calls go through a proxy or an LLM gateway, it may not match the provider that actually served the request.

A worked example: sampling an agent fleet

Say a platform runs 10,000 agent traces a day, 1% of them (100) fail, and you can afford to keep 20%.

Head sampling decides at the start of the trace, usually from the trace ID itself, so every service reaches the same answer without talking to the others. It keeps \(r \times N\) traces:

\[ \text{kept} = 0.2 \times 10{,}000 = 2{,}000 \]

That's cheap and simple, but at the moment of deciding nobody knows which runs will fail. So it keeps only \(0.2 \times 100 = 20\) of the 100 failures. The traces you most need are exactly the ones it throws away.

Tail sampling waits until the trace is finished and then decides with full knowledge, for example "every trace with an error, plus 20% of the rest". With \(E\) error traces:

\[ \text{kept} = E + r \times (N - E) = 100 + 0.2 \times 9{,}900 = 2{,}080 \]

For 80 more traces (about 4% more storage), all 100 failures are on file. The catch is where it runs. Tail sampling needs a collector that holds every in-flight trace in memory until it ends. That's fine for a quick web request. It's much harder for an agent run that takes minutes, or that pauses to wait for a human to approve something.

The second half of the answer is metrics. The GenAI conventions define histograms (bucketed counts) that are recorded for every operation, sampled or not: agent duration, tool duration, the number of model and tool calls per invocation, time to first token and time per output token. Time per output token separates generation speed from the wait before the first token:

\[ \text{TPOT} = \frac{T_{\text{request}} - T_{\text{first}}}{n_{\text{out}} - 1} \]

In plain words: take the total time, subtract the time to the first token, and divide by the tokens produced after the first one. A 4.2 s request whose first token arrived at 0.6 s and which produced 181 tokens works out to \((4.2 - 0.6) \div 180 = 0.02\) s per token. Dashboards and alerts should be built on metrics like this, because they see all the traffic. Sampled traces are for drilling into individual runs.

Architecture and production implications

The default trace has no words in it. This one surprises people. Prompts, replies, system instructions, tool arguments and tool results are treated as sensitive and are off by default. One setting, OTEL_INSTRUMENTATION_GENAI_CAPTURE_CONTENT, controls it. The options are NO_CONTENT (the default), SPAN_ONLY, EVENT_ONLY or SPAN_AND_EVENT, and an unrecognised value falls back to no content, so a typo fails closed. Events go through OTel's logs pipeline, which means they can sit in a different store with its own access rules and retention. For production the conventions point to a third option: a hook you supply uploads the messages to object storage and puts only the address on the span, in gen_ai.input.messages_ref and its siblings. The hook runs whatever the sampler decided, so content is kept even for traces that get dropped. My take: decide this per environment before your first incident. Debugging a wrong answer from a trace with no words in it is a bad afternoon.

Whatever you propagate, everyone downstream sees. Baggage (key-values carried along with the trace context) gets added to outgoing headers, including calls to third-party APIs. Put a session ID in it. Never put an email address in it.

Short-lived code loses spans. A serverless handler or batch job can end with spans still sitting in the queue. Call flush() or shutdown() before you return, every time.

Choose where masking runs. Mask in the application when data must never leave the process. Mask in a collector when you want one consistent policy across many services and the collector is inside your trust boundary. Either way, filter whole traces where you can. Dropping a parent span while keeping its children leaves orphans that no UI can place.

The conventions are still moving. Every gen_ai.* attribute, span and metric is at Development status, and there's no schema URL yet to translate old names into new ones automatically. Only the borrowed core attributes like error.type and server.address are stable. In practice that means pinning instrumentation versions, checking how your backend reads a given library's spans, and re-checking dashboards on every upgrade.

What I'd do differently. I'd name every agent and workflow deliberately on day one, because that name becomes the span name, the metric dimension and the sampling key all at once. I'd propagate context at every boundary I own (HTTP headers between services, _meta on MCP calls, message attributes on queues) before writing a single dashboard. And I'd decide the content-capture policy alongside the data-retention policy, not after it.

Takeaways

  • OTel is three ideas: spans in a shared format, a traceparent label that travels with every request, and a batching pipeline that can export to any backend.
  • Broken traces are almost always a missing propagation step. For MCP, the context travels in _meta, not a header.
  • The GenAI conventions give agent runs a common shape: invoke_agent, chat and execute_tool, with low-cardinality names set when the span starts.
  • Head sampling is cheap but blind. Tail sampling keeps the failures but needs memory, which is hard for long agent runs. Metrics cover the gap because they count everything.
  • Content capture is off by default. In production, store content separately and keep only a reference on the span.

The picture I keep coming back to is a restaurant order ticket. The waiter writes the table number on it, every station adds its start and finish times, and the ticket travels with the food. At the end of the night you can lay the tickets out and see where each order spent its time, whoever ends up doing the accounts. I'm curious which boundary in your stack was the last one to get a traceparent.
