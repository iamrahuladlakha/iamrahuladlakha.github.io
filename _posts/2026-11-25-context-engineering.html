On a long agent task I care more about the text the model has to reread on every call than about another pass over the wording. The job I keep using as a test sounds ordinary: analyse sales data and create a report. It ran five stages, took about 15 minutes, and used over 150,000 tokens. Kept in one context, a 200,000-token window overflows before that report is finished. One tool returned a browser page of about 17,000 characters, and from then on every later call was carrying that page too.

Prompt engineering is how you word the instruction. Context engineering is the decision about what this call is allowed to see. The harness is the world around that call: the files, the tools, the checks. I spent a long time on the wording. The runs that actually finished were the ones where I got serious about the other two.

The window fills before the work is done

An agent here is a model that can call tools and take several steps. A token is the chunk of text the model counts, often a word or a piece of a word. The context window is how much of that text one call can read. Every tool result and every message stays in the history, and the next call sends the history again. Nothing in that pile expires on its own.

Picture the desk at the end of a day, every page you touched still sitting on it. The sheet with the number you need is in the pile. There is still some bare desk showing, and you still cannot put your hand on the number. Models do the same thing. As the context grows they get worse at recalling and using what is already in it, while the window still has room. Close to the limit, some of them start rushing to wrap up. After that the window simply overflows and the call fails.

So I assign the window like a budget: what is allowed in, and what has to live in a file.

Four layers, each catching what the one before missed

I plan the context in four layers. Isolate, so each agent has its own window and only a compressed summary crosses the boundary. Limit what each agent is allowed to return, and write that cap into its instructions. Keep bulky content in files, with a short note and a path in the context. Then verify with a separate check, and keep a safety net for the day the window fills anyway.

The sales-report task is the run I step through below. The numbers are from that run.

The validator is there because a summary, and a 30-token note, can both be wrong. I want a second pass that re-runs the calculations.

Show a catalogue, and load one guide when it is picked

Skills are the clearest place I see this. A skill is a packaged way of doing one kind of job, with a name, a short description and a longer guide. If I paste every guide into the prompt, I pay for all of them on every call, including the ones this task will never touch.

The pattern I use is a catalogue. The short description of each skill is always in the prompt. The full guide is added only for the skill the agent actually picks. In symbols, the cost of that part of the context is

\[ \text{context cost} \approx \sum_i \text{description}_i + \text{guide}_{\text{chosen}} \]

The sum is every skill’s short description, and it is on every call. \(\text{guide}_{\text{chosen}}\) is added only for the skill in use. A catalogue of about 500 tokens, set against over 20,000 tokens of full guides, is roughly 97% less in the prompt. Taking 20,000 as that full figure, \(1 - 500 \div 20{,}000 = 0.975\), or 97.5%. Open one skill and the call carries \(500 + 3{,}000 = 3{,}500\): \(1 - 3{,}500 \div 20{,}000 = 0.825\), or 82.5% less than loading every guide.

The calculator starts on those three figures. What I want on the call is a small list that is always there, and one long document at the moment it is needed.

Trim what the tool returns, not the text you already have

Three habits sit next to the layers. The third is the one I have actually shipped by mistake.

Return less. A browser tool should hand back a compact view of the interactive elements. The 17,000-character page is what sending the whole page costs.

Batch inside a script. Let the agent write a short script that chains several tool calls. The pages in the middle of that script never enter the context. Only the script’s final result does.

Do not trim afterwards. I have seen a team cap a bloated page at 8,000 characters once it was already in hand. Try this before you read what happened. It is a different experiment from the cost comparison later in the post.

What was triedWhat happened
Cap a returned page at 8,000 charactersThe agents fetched the page again. Cost per successful task stayed flat.
What works insteadMake the tool return a compact result in the first place, or chain the calls in a script so the intermediate pages never enter the context.

When the window fills anyway

Even with all of that, a long run can fill the window. I have two moves, and I keep the same things word for word through either of them: plans, checklists and clues.

Compaction summarises the older history in place and keeps the same agent going. The thread continues, and so does any hole the summary left, because the next step reads the summary rather than the original messages.

A reset starts a fresh agent from a structured handoff. The new window is empty, so the handoff has to carry the state or the new agent starts without it. I write that handoff as a file the next agent reads.

Either way, the messages that were summarised stay on disk. If those originals are gone, anything the summary skipped is gone with them.

In a harness I implement this as small bits of code at fixed points in the loop: before the run, around each model call, around each tool call. Each one moves context out of the window and leaves a way back. Hover, focus or tap a row to see when it fires.

TechniqueWhen it runsWhat it does
OffloadingAfter each tool callA result over about 20,000 tokens is saved to a file. The model sees the first and last few lines plus the path. Pasted user messages get the same treatment above 50,000 tokens. A 40,000-row export is offloaded immediately.
SummarisationBefore each model callAt 85% of the window, older messages are condensed. On a 200,000-token window that is \(0.85 \times 200{,}000 = 170{,}000\) tokens. The latest messages stay word for word. The originals are saved, and each later summary includes the previous one.
SkillsBefore the run, then each callName and description only, until the skill is used. About 500 tokens of catalogue instead of over 20,000 of guides.
SubagentsWhen the model delegatesThe noisy work runs in its own context. Only the result comes back.
Long-term memoryStart, each call, and when it learnsA plain file is loaded into the system prompt and updated when something is worth keeping past this run.

Two rules sit under all five. Offload, and keep the file: cutting a result throws away the part you may need later. Compaction has to be recoverable, so the summarised messages stay on disk and the agent can reread them. A 40,000-row export should be a file from the start. What actually fills the window is the slow climb of searches and drafts. I also summarise when the topic changes, and I tune the 85% threshold to the task.

One kind of context never shows up in a file: taste, house style, how hard to push. It arrives when a person looks at the work and says what was off. I scope the agent so that correction is easy to give. A narrow job, a visible draft, a place for the comment to land.

Three cases

A sales report

Five stages, about 15 minutes, over 150,000 tokens. In one context a 200,000-token window overflows mid-task. Split it, and the coder’s own window stays under 25,000 tokens, coming back with 1,000 to 1,500. The validator returns 800 after re-running the calculations, the reporter about 1,000, and the hand-off is about 30 tokens plus a path, or “Wrote 105 lines, execution successful.” Shared state is four small fields. Results, citations and audit notes move as files.

A browser task

I came across a comparison of browser toolsets on the same tasks, with the same model. Only the text that entered the context changed. One side put full pages into the window: about 26 model turns per task, 78% success, $26.71 in total. The other returned compact snapshots, and let the agent chain calls in a short script: about 10 turns per task, a navigation of median 117 characters instead of about 17,000, 90% success, $1.98 in total.

\(26.71 \div 1.98 = 13.5\), which is the “about 13 times cheaper” I quote, and success moved from 78% to 90%. Same model. What changed is what the tool put in the window. Keep this separate from the 8,000-character cap: that one left the cost per success flat, because the agent fetched the page again.

A support desk

I do not have a measured bill for a support deployment, so this is the design I would write, using the same thresholds as the two cases above.

The agent answers from a folder of policy articles. The folder stays on disk. The prompt gets a catalogue of short descriptions, about 500 tokens in the skills pattern, and one article loads when the agent picks it, the way a skill loads one guide of about 3,000 tokens. A pasted thread above 50,000 tokens is written to a file, and the model sees the ends plus the path. A tool result over about 20,000 tokens is offloaded the same way. On a 200,000-token window I summarise at \(0.85 \times 200{,}000 = 170{,}000\) tokens, keep the latest messages word for word, and leave the originals on disk.

The customer-facing reply stays short, with the long reasoning in a file, along the lines of the reporter cap of about 1,000 tokens. A second step checks the reply against the article. Tone, how firm to be on a refund, still only arrives when a person marks a reply. I would keep the job narrow enough to review in one sitting.

What I would actually run

Cost. The browser comparison is the cleanest bill I have: $26.71 at 78% success against $1.98 at 90%, \(26.71 \div 1.98 = 13.5\), about 13 times cheaper, and about 26 turns down to about 10. The other lever is prompt caching. Put the stable prefix first, the system prompt and the tool list, and put whatever changes last: the latest tool result, the new message. The serving stack can reuse the work it already did on that front, which can cut the cost of the repeated input by up to 90%. I turn caching on for an agent that is called often with the same prompt, and off for a one-shot agent.

Latency. Every turn resends the history, so a long run pays for the old tool output again and again. The sales task took about 15 minutes and over 150,000 tokens. The compact browser setup finished in about 10 turns instead of about 26: fewer model calls, and less text on each of them.

Where it breaks. Every summary loses something the next step might have needed, so I keep plans, numbers and decisions word for word, with the full text in a file the agent can reopen. Isolation keeps each window small and adds agents, hand-offs and a prompt per agent. The 8,000-character cap sent the agent back for the full page and left the cost per success flat. Recall also gets worse while the window still has room, so a context that is only partly full can already be unreliable.

What I would do differently next time. Budget tokens per agent the way I budget memory per service: an output cap in the instructions, and a measurement of how big that agent’s context actually got. Hand work off through files. Offload a long result to a file rather than cutting it off, and make every summary recoverable. Cache the agents that repeat a prompt, and skip the cache on the one-shot ones. Retune the thresholds per task, and summarise on a topic change as well as at 85%. Scope the job so a person can correct tone and house style, because that context will never arrive from a file.

What this means for leaders. The context window is both a cost line and a reliability line. Full browser pages in one comparison cost $26.71 at 78% success; compact results plus short scripts cost $1.98 at 90%, about 13 times cheaper, on the same model and the same tasks. The risk is recall slipping while the window still has room, and a summary that drops a number the next step needed. Set a token budget per agent, keep bulky results in files, and check the work in a separate step. Ask the team for each agent’s context size on a real task, what is written to a file instead of cut short, and which plans stay word for word through a summary.

Takeaways

  • Decide what each call is allowed to see. Wording the instruction, and building the tools around the model, are separate jobs.
  • Four layers: isolate each agent, cap what it returns, point at files, then verify with a second pass that re-runs the work.
  • A 500-token catalogue instead of 20,000 tokens of guides is 97.5% less. One 3,000-token guide brings that call to 3,500.
  • An 8,000-character cap after the fact left the cost per success flat. The tool has to return less in the first place.
  • Offload past about 20,000 tokens, summarise at 85% (170,000 tokens in a 200,000 window), and keep the originals on disk.
  • On the browser tasks, compact results and chained calls moved the bill from $26.71 to $1.98 and success from 78% to 90%.

The desk picture is the one I come back to. Today’s plan and a few notes on top, everything else in a labelled folder, and a one-page note from the team that says the full analysis is in the shared drive. I would like to hear which of the four layers people put in first, and which threshold they ended up retuning once a real task had run.
